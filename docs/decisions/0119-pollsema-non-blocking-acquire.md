# ADR 0119: `PollSema` and non-blocking semaphore acquisition

- **Status:** Accepted.
- **Date:** 2026-11-10.
- **Context:** After the modelled IOP reset completion (ADR 0118) the real-title probe advances past `SifIopSync` and re-runs the EE's SIF initialisation, then stops as `unhandled_syscall` service `0x45` at `0x0025A734` with `$a0 = 4`. The layer modelled CreateSema/DeleteSema/SignalSema/iSignalSema/WaitSema but not the non-blocking poll.
- **Evidence:**
  - **Observed (PS2SDK `ee/kernel/include/syscallnr.h`):** `__NR_WaitSema 0x44`, `__NR_PollSema 0x45`, `__NR_iPollSema (-0x46)`, `__NR_ReferSemaStatus 0x47`, `__NR_iReferSemaStatus (-0x48)`.
  - **Observed (PS2SDK `ee/kernel/include/kernel.h`):** `extern s32 PollSema(s32 sema_id);` and `extern s32 iPollSema(s32 sema_id);` — one argument, `int` result. `MAX_SEMAPHORES 256`.
  - **Observed (ps2tek, EE syscalls):** `44h void WaitSema(int sema_id)` — "If the semaphore's `count` variable > 0, count is decremented. Else, a thread rescheduling occurs ... status is set to WAIT"; `45h int PollSema(int sema_id)` / `46h int iPollSema(int sema_id)` — "Decrements the semaphore's count variable. Returns -1 if unsuccessful." The contrast in wording is the documented difference between the two: only the wait reschedules.
  - **Observed (boot ELF, local evidence):** at `0x0025A730`..`0x0025A73C` the words are `24030045` (`li $v1,0x45`), `0000000C` (`syscall`), `03E00008` (`jr $ra`), `00000000` (`nop`) — a single-argument thunk whose result is `$v0`. The wrapper at `0x00246FA0` loads the semaphore id into `$a0`, calls the thunk, reloads the same id into `$v1`, and branches on `bne $v1,$v0` (`14620029`) to its bail path. The delay slot sets `$v0` to zero for that bail path; therefore a call that returns the same id has succeeded. The first of the other callers, `0x00246068`, independently treats negative values as failure (`bgez $v0` at `0x0024606C`) and signals that semaphore on success. No caller of the `ReferSemaStatus` thunk at `0x0025A750` exists in this image.
  - **Observed (real-title probe before return correction):** the service was handled, and diagnostic counters showed the first poll observed count `1` and two calls consumed counts (`poll_sema_first_count=1 poll_sema_acquired_total=2`); the title still exhausted its budget in the caller loop at `0x00246DAC`. This did not show that the service never acquired a count; it showed that returned `$v0` failed the equality test.
  - **Observed (synthetic regression):** `reps2_hle_syscall_codegen_smoke` creates semaphore ID 1 and verifies that successful `PollSema(1)` returns 1; with the prior return-0 behavior it failed at assertion 942, then passed after the correction.
  - **Unknown:** ps2tek does not state the exact success value; the image-derived wrapper contract establishes it for the observed target. `ReferSemaStatus`/`iReferSemaStatus` have no primary description and no caller in this image.
- **Decision:** Model `PollSema` (0x45) and `iPollSema` (0x46, resolved by magnitude like the other `i` aliases) as a non-blocking acquire sharing the existing semaphore table:
  1. Resolve `$a0` to a live object through the same lookup every other semaphore service uses.
  2. When the object exists and its count is positive, decrement it and return the semaphore id. This success value is derived from the retail wrapper at `0x00246FA0`, which compares the returned `$v0` against the id it passed.
  3. Otherwise return the documented failure `-1`: a zero count and an id that names no live object are both "unsuccessful". The completion is `Status::ok` in every case — a poll never blocks, so `Status::semaphore_wait_blocked` remains exclusive to WaitSema.
  4. The observed count before the call, whether a count was consumed, and a call counter are recorded for probes and sessions. No thread is made runnable, no waiter list is touched, and the count is never raised.
- **Alternatives considered:**
  1. Alias 0x45/0x46 onto `WaitSema` — rejected: the documented poll is the non-blocking form; blocking the run there would stop a guest that is written to continue on `-1`.
  2. Return `-1` for a zero count and stop the run as `semaphore_wait_blocked` — rejected: that would fabricate a block the SDK poll path does not have.
  3. Implement `ReferSemaStatus` (0x47) at the same time — rejected: no primary description of its fields-and-return contract and no caller in the observed image, so it stays fail-closed as `unhandled_syscall` rather than being guessed.
- **Consequences:** a successful poll returns the ID the retail caller expects; an empty or invalid semaphore returns `-1`, and polling never blocks. This does not identify or implement the producer that must later signal the observed semaphore.
- **Validation:** `reps2_hle_syscall_codegen_smoke` covers a positive count with nonzero id (consumed and returns that id), a zero count (returns `-1` without blocking and leaves the count unchanged), an id naming no live object (returns `-1` without acquisition), and dispatch of both `0x45` and negated `0x46` to the same handler. The nonzero-ID assertion failed with the prior return-0 implementation (assertion 942) and passed with the corrected result; the full HLE smoke then passed all 118 cases. A regenerated real-title probe is required to establish the next execution frontier; the prior PostPR69 trace is pre-correction evidence only.
