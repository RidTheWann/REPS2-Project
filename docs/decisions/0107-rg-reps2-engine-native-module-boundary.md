# ADR 0107: RG REPS2 ENGINE native-module boundary

- **Status:** Accepted; revised for descriptor ABI v1 and engine ABI v2.
- **Date:** 2026-11-09.
- **Context:** REPS2 has a Rust AOT frontend, deterministic C++20 code generation, a generated-code runtime ABI, and a synchronous native session core. A real engine must load compiled native artifacts without introducing per-guest-instruction dispatch overhead or exposing implementation-specific C++ library types across a shared-library boundary.
- **Decision:** RG REPS2 ENGINE keeps the Rust frontend, generated C++20 guest dispatcher, and C++20 runtime as the semantic source of truth. A compiled module exports exactly one descriptor getter, `rg_reps2_get_native_module_descriptor_v1`, with C linkage. The getter returns a pointer to a versioned, standard-layout, trivially-copyable POD descriptor.
- **Descriptor contract:** The descriptor contains its exact structure size, descriptor ABI version, bounded module name bytes, engine ABI version, runtime ABI version, toolchain/layout fingerprint, target architecture/OS, reserved fields, and two noexcept callbacks. The callbacks use fixed-width integer arguments, raw byte pointers, and an opaque `void*` guest-state pointer; no `std::string_view`, `std::span`, STL containers, C++ references, exceptions, virtual interfaces, or ownership-bearing C++ values cross the exported C ABI.
- **Runtime layout guard:** The opaque state pointer is interpreted as the current `reps2::runtime::EeState` inside the module. Admission therefore requires the same engine/runtime ABI and a compile-time fingerprint of compiler, standard-library ABI, language mode, exception/RTTI/iterator settings, pointer size, and the sizes/alignments of the shared runtime state types. The runtime ABI version remains the semantic compatibility authority and must be incremented when guest-visible state layout/contracts change. The fingerprint is a compatibility guard, not a cryptographic attestation or a sandbox.
- **Admission:** The engine validates descriptor size/version/reserved fields, safe module-name syntax and length, engine/runtime versions, toolchain fingerprint, target, and both callbacks before publishing a prepared handle. Admission is transactional; a rejected descriptor leaves the caller's prior handle unchanged. Invalid callback status values are converted into an explicit engine error rather than cast into an unknown runtime status.
- **Platform loading:** The loader canonicalizes the supplied file path and requires a regular file. Windows uses `LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`; ELF/macOS uses `dlopen` with `RTLD_NOW | RTLD_LOCAL` and `dlsym`. Android uses the NDK's `libdl` interface when built for Android. The loader does not search the working directory or an ambient plugin path for the primary module.
- **Lifetime policy:** Loaded libraries are pinned for process lifetime; `FreeLibrary`/`dlclose` and hot-unload are deliberately unsupported. Prepared handles retain shared host ownership and each EngineSession copies that ownership, so dropping the caller's handle cannot invalidate an active session. The process-lifetime pin avoids unmapping code that may still be referenced by callbacks or module TLS. A future unload design requires explicit execution quiescence and module-owned thread/TLS teardown contracts.
- **Trust boundary:** A native module is executable code with the host process's privileges. The loader does not sandbox code, validate a publisher signature, or attest the artifact's provenance. Only modules from a trusted source may be loaded. A malformed or incompatible descriptor is rejected after the OS loader has mapped the library and run its native initialization; rejection is not a security sandbox.
- **Execution contract:** The engine invokes module initialization once during session start and invokes its budgeted execution callback once per `run()`. Guest block/instruction dispatch remains inside generated native code. No per-instruction C/Rust FFI, interpreter callback, socket, background polling thread, or engine-owned file I/O is introduced.
- **Build integration:** `RG::REPS2Engine` is a static CMake library containing the platform loader and public C++20 headers; its runtime dependency and platform dynamic-loader library are linked by the target. CI builds and loads an actual shared-library fixture on Windows/MSVC and Linux/GCC.
- **Alternatives considered:**
  1. Export C++ objects containing `std::string_view`, `std::span`, or STL containers — rejected because those types make the shared-library ABI dependent on compiler and standard-library implementation details.
  2. Export callbacks taking C++ references and spans directly — rejected in favor of a fixed-width C ABI and opaque state pointer, while still checking the exact runtime/toolchain contract behind that pointer.
  3. Unload modules immediately when the last session closes — deferred because ELF dynamic-linker guidance calls out TLS/symbol lifetime complexity around `dlclose`; the engine pins modules for process lifetime instead.
  4. Add per-instruction callbacks — rejected because the generated CFG dispatcher already performs guest dispatch in native code and must remain the hot execution loop.
- **Consequences:** RG REPS2 ENGINE can admit and invoke trusted native shared modules on the tested Windows x64 and Linux x64 builds. The code path is prepared for POSIX dynamic loading on Android/macOS, but those targets are not yet CI-validated; Android native release support is not claimed. The engine still has no frontend-produced module wrapper/package, signature verification, hot-unload, AArch64 machine-code backend, complete PS2 device runtime, real-title boot proof, or performance benchmark.
- **Validation:** CTest loads a real shared fixture, verifies copied module identity and ABI admission, exercises missing-symbol and missing-file failures without overwriting the prior prepared handle, starts a session, drops the caller's module handle, and proves the session can still invoke its module. The existing generated CFG fixture continues to verify actual guest state, budget pause/resume, and external-control-flow reporting on Windows/MSVC and Linux/GCC.
