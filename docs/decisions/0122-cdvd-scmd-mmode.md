# ADR 0122: Implement the first CDVD S-command — `CD_SCMD_MMODE` (0x22)

- **Status:** Accepted.
- **Date:** 2026-11-10.
- **Context:** The PostPR72 probe (after ADR 0121) shows the title's first S-command on the CdSCmd server (`0x80000593`): `sif_rpc_call_number=34` (decimal 34 = `0x22` `CD_SCMD_MMODE`) with a 4-byte payload whose first word is `rpc_call_req=0x00000002`, send/recv both 4 bytes. Because the handler refused it, no `SIF_CMD_RPC_END` was sent and the caller blocked (`stage=semaphore_wait_blocked`, `pc=0x0025A724`, 3,173,557 instructions). The next unit is the body of that exact command.
- **Evidence:**
  - **Observed (PS2SDK `ee/rpc/cdvd/src/scmd.c`):** the `CD_SCMD_CMDS` enum places `CD_SCMD_MMODE` at `0x22` and `CD_SCMD_SETTHREADPRI` at `0x23`; `sceCdMmode(int media)` sends exactly one `s32` (`sCmdSendBuff.s32arg = media`, `sceSifCallRpc(..., CD_SCMD_MMODE, 0, &sCmdSendBuff, 4, sCmdRecvBuff, 4, ...)`) and returns `*(int *)sCmdRecvBuff` — a single 4-byte result word.
  - **Observed (PS2SDK `common/include/libcdvd-common.h`):** `enum SCECdvdMModeMediaType { SCECdMmodeCd = 1, SCECdMmodeDvd }` (so the observed `2` is DVD); `sceCdMmode` is documented "@return 1 on success, 0 on failure. SUPPORTED IN XCDVDMAN/XCDVDFSV ONLY".
  - **Observed (PS2SDK `iop/cdvd/cdvdman/src/cdvdman.c`):** the IOP-side `sceCdMmode` is exactly `g_cdvdman_mmode = media; return 1;` — it stores the requested media mode and returns 1; it does not query a disc.
  - **Observed (PS2SDK `iop/cdvd/cdvdfsv/src/cdvdfsv.c`):** `cbrpc_rpc3_cdvdscmds` dispatches function `0x22` to `cdvdfsv_rpc3_22_mmode`, which does `if (buflen == 4 || !inbuf->m_pkt_22.m_char4) outbuf->m_retres = sceCdMmode(inbuf->m_pkt_22.m_media);` — so a 4-byte request sets `m_retres = 1`. `common/include/libcdvd-rpc.h` confirms `cdvdfsv_rpc3_22_inpacket_t { int m_media; char m_char4; }` and that the outpacket union's first member is `int m_retres`.
  - **Observed (real-title probe, PostPR72):** first S-command is `0x22` with request word `2` (`SCECdMmodeDvd`), 4-byte send/recv, no reply.
- **Decision:** Model `CD_SCMD_MMODE` (0x22) in `serve_ee_cdvd_scmd_call`. When the RPC function number is `0x22` and the request is exactly the documented 4-byte payload with a readable request word and a writable 4-byte reply buffer, the HLE CDVD driver stores the media word (`cdvd_mmode`, mirroring `g_cdvdman_mmode`), writes `m_retres = 1` into the caller's receive buffer, and returns true so the dispatcher sends `SIF_CMD_RPC_END` and raises the caller's semaphore. Any other S-command number, or a malformed MMODE request (send size != 4, or unreadable request / unwritable reply), is refused: the handler returns false, no reply packet is sent, and the caller stays blocked — the honest fail-closed boundary, not a fabricated answer. Returning 1 is not a fake success here because the real IOP handler also just stores the mode and returns 1; the mode switch is recorded as guest-observable state, and no disc presence is implied (`sceCdMmode` is a mode switch, not a media query).
- **Alternatives considered:**
  1. Refuse MMODE too and only record it — rejected: this is the exact command the title issues first, and its real IOP behavior is fully known (store mode, return 1), so refusing it only stalls the title with no evidentiary gain.
  2. Return the echoed media word or 0 — rejected: both contradict the IOP implementation (`return 1`) and the header contract; that would be a fabricated result.
  3. Model the full guard (`buflen == 4 || !m_char4`) for send sizes > 4 — rejected as out of scope: the EE SDK only ever sends 4 bytes for MMODE and the probe confirms 4; a non-4 request fails closed instead of guessing the stale `g_outbuf` path.
- **Consequences:** The MMODE call now completes, the title's `sceCdMmode` returns 1, and execution resumes past the call. New probe fields (`scmd_calls`, `scmd_replies`, `last_scmd_number`, `last_scmd_media`, `last_scmd_retres`, `last_scmd_replied`, `cdvd_mmode`) make the S-command boundary machine-readable. All other S-commands still block, so the next observed S-command names the next unit. The driver's media mode is now recorded, which later disc-dependent S-commands (e.g. `GETDISKTYPE`) can read.
- **Validation:** `reps2_hle_syscall_codegen_smoke` adds two cases (124 total). (1) An MMODE call (`0x22`, 4-byte payload `2`) on `0x80000593` records `scmd_number=0x22`, `cdvd_mmode=2`, `last_scmd_retres=1`, `last_scmd_replied`, `scmd_replies=1`, writes `1` into the reply buffer, increments `rpc_call_replies`, and the `SIF_CMD_RPC_END` raises the caller's semaphore. (2) A malformed MMODE (8-byte send) is refused: no reply word written, no RPC_END, `scmd_replies=0`. The regenerated PostPR73 probe then reports `scmd_calls=1 scmd_replies=1 scmd_number=34 scmd_media=0x00000002 scmd_retres=0x00000001 scmd_replied=1 cdvd_mmode=0x00000002`, `sif_rpc_call_replied=1`, and execution is no longer blocked: `stage=budget_exhausted`, `executed=4,999,997`, `pc=0x00247AD0` (previously `semaphore_wait_blocked` at `0x0025A724` with 3,173,557 instructions). The next frontier is the loop now running at `0x00247AD0` under the 5,000,000 budget.
