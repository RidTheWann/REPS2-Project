# ADR 0126: Admit control-flow targets that enter a delay slot

- **Status:** Accepted.
- **Date:** 2026-11-11.
- **Context:** ADR 0003/0017 rejected any control-flow target landing on another instruction's delay slot (`AnalysisError::TargetEntersDelaySlot`), and the analyzer reported such targets as skipped/unresolved. The Downhill Domination probe stopped as `unresolved_control_flow` at `pc=0x0025C774`: `0x0025C770 beq $t2,$zero -> 0x0025C7C4` has delay slot `0x0025C774`, and the cache-writeback loop's `0x0025C7BC bgtz $t2 -> 0x0025C774` branches back into that delay slot. On MIPS/R5900 hardware a jump directly to a delay-slot address executes that word as an **ordinary** instruction — delay-slot-ness belongs to the branch, not the address — so rejecting the target is not hardware-faithful.
- **Evidence:**
  - **Observed (real-title probe, branch on `8c24f19`, Windows x64/MSVC):** before this change the engine runner stopped `unresolved_control_flow @ 0x0025C774` after 3,889,750 instructions; decoded words around it are verbatim `beq`/`addiu`/`sync`/`cache`/`bgtz` as above.
  - **Observed (after this change):** the same module regenerated with 60,484 blocks (was 60,466) including `block_0x0025C774`, and the probe advances past the loop to a new stop `unresolved_control_flow @ 0x80076440` (inside the declared relocated-code region `0x80076000..0x80076740`) after 3,890,249 instructions, syscalls 149 seen / 131 handled. The delay-slot loop is now traversable.
  - **Observed (unit tests):** branch target into a delay slot, backedge from a later block into a delay slot, and a heuristic root at a delay-slot address are all admitted as ordinary block starts; the owning branch block keeps the same word as its delay slot.
- **Decision:** In `build_cfg`, a queued target whose owner is `OwnerLocation::DelaySlot` is admitted as a new block start (for authoritative and heuristic edges alike, because the address is already proven code). `fetch_delay_slot` no longer rejects a delay-slot address that is also a block start (shared word, dual role — exactly the hardware behavior); it still rejects when the delay-slot address is interior to a *different* block. `register_block_owners` lets a block starting at a delay-slot address replace the `DelaySlot` marker, and lets the owning branch keep the existing block-start owner when it registers later (insertion order is queue-dependent). Split logic for `Body`/`Control` interiors is unchanged. Control transfers inside a delay slot remain rejected (ADR 0037); only SYSCALL/BREAK are admitted there.
- **Alternatives considered:**
  1. Keep rejecting and patch the title — rejected: title-specific control-flow suppression would violate the shared-semantics rule, and the behavior is hardware-legal.
  2. Admit only authoritative targets — rejected: the real frontier's backedge arrives through a heuristic-discovered block, so authoritative-only admission leaves `0x0025C774` unresolved (verified: 60,474 blocks without it vs 60,484 with).
  3. Redirect the edge to the owning branch instead — rejected: that would change taken-branch semantics (hardware executes the target word normally, then continues at target+4).
- **Consequences:** CFG coverage grows (60,466 → 60,484 blocks on the Downhill boot image) and the M4 frontier moves past the `0x0025C774` cache-writeback loop to `0x80076440`, which lies inside the declared relocated-code region but is still not a translated block — the next unit is to find why control flow reaches an undeclared/mid-region address there (likely an indirect jump through the copied code or a region-boundary edge). Supersedes the "reject delay-slot-entry targets" rule in ADR 0003/0017 for the CFG policy; ADR 0037's delay-slot trap rules are unchanged.
- **Validation:** `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --locked` (343 lib tests incl. 3 new delay-slot-entry cases), CMake Release build, `ctest -C Release` 40/40 on Windows x64/MSVC.
