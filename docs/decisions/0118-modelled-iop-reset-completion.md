# ADR 0118: Modelled IOP reset completion and the post-reset SIF flags

- **Status:** Accepted.
- **Date:** 2026-11-10.
- **Context:** After `sceSifStopDma` (ADR 0117) the real-title probe follows the retail `SifIopReset` prologue: it sends the `SIF_CMD_RESET_CMD` packet (`cid` `0x80000003`, `psize` `0x68`) and then spins for the whole 5,000,000-instruction budget in the `SifIopSync` poll at `0x0025ED10`, which re-reads `SMFLAG` and tests `SIF_STAT_BOOTEND` (`0x40000`). The modelled IOP never reboots, so the flag never appears.
- **Evidence:**
  - **Observed (PS2SDK `ee/kernel/src/iopcontrol.c`):** `SifIopReset` calls `sceSifStopDma()`, fills `SifCmdResetData_t` (`header.psize = sizeof`, `header.cid = SIF_CMD_RESET_CMD`, `arglen`, `mode`, `arg[80]`; `dsize` uninitialised), DMAs it to `SIF_SYSREG_SUBADDR` with `SIF_DMA_ERT | SIF_DMA_INT_O`, then writes `SMFLAG` `SIF_STAT_BOOTEND`, `SIF_STAT_SIFINIT`, `SIF_STAT_CMDINIT`, `SIF_SYSREG_RPCINIT = 0` and `SIF_SYSREG_SUBADDR = 0`, returning `1` when the DMA started. `SifIopSync()` returns `(sceSifGetReg(SIF_REG_SMFLAG) & SIF_STAT_BOOTEND) != 0`.
  - **Observed (boot ELF, local evidence):** the retail `SifIopReset` at `0x25EBD0` performs exactly that sequence with the packet at `0x00765140` (`psize` byte `0x68`, `cid` `0x80000003` at `+8`, `mode` at `+0x14`, `arglen` at `+0x10`, argument bytes from `+0x18`), a single-entry `SifDmaTransfer_t{src, dest = SUBADDR, size = 0x68, attr = 0x44}` on the stack, and register writes `SetReg(4, 0x40000)`, `SetReg(4, 0x10000)`, `SetReg(4, 0x20000)`, `SetReg(0x80000002, 0)`, `SetReg(0x80000000, 0)`. `SifIopSync` at `0x25ED10` is `(GetReg(4) & 0x40000) != 0`. Its caller at `0x20DF60` retries `SifIopReboot` while it returns `0` and then loops at `0x20DF80` as `while (!SifIopSync())`.
  - **Observed (PS2SDK `iop/system/sifman/src/sifman.c`, `iop/system/sifcmd/src/sifcmd.c`):** the IOP-side modules are what publish those flags. `sifman`'s `sceSifInit` waits for `MSFLAG & SIF_STAT_SIFINIT`, then writes `SMFLAG = SIF_STAT_SIFINIT`; `sifcmd`'s `sceSifInitCmd` writes `SMFLAG SIF_STAT_CMDINIT` and waits for the EE's `INIT_CMD` event, and its `INIT_CMD` handler stores the EE receive buffer and acknowledges on `MSFLAG`. The EE-side `sceSifInitCmd` pairs with this: after a reset clears `SIF_SYSREG_SUBADDR`, it waits `while (!(sceSifGetReg(SIF_REG_SMFLAG) & SIF_STAT_CMDINIT))`, re-publishes `SYSREG_MAINADDR` and sends `SIF_CMD_INIT_CMD`.
  - **Observed (ps2tek SIF map; PCSX2 `pcsx2/HwWrite.cpp`):** EE `0x1000F220` is `MSFLAG` (EE→IOP) and `0x1000F230` is `SMFLAG` (IOP→EE); PCSX2 implements the EE's `MSFLAG` write as `psHu32 |= value` and the EE's `SMFLAG` write as `psHu32 &= ~value`, i.e. the EE *clears* IOP→EE flag bits, which is why `SifIopReset` clearing `BOOTEND`/`SIFINIT`/`CMDINIT` before the reboot can then wait for the IOP to assert them again.
  - **Observed (real-title probe after ADR 0117):** `sif_cmd_cid=0x80000003` with `sif_stop_dma=1 sif_stop_dma_cleared=0`; `status=budget_exhausted`, `pc=0x0025ED10`, `executed=5000000`.
  - **Derived:** the title's post-CdInit path is an IOP *replacement* (`IOPRP270.IMG` plus its IRX set), not a CDVD read, and the boot stage it waits for is the IOP finishing that reboot.
- **Decision:** Model the requested reset as a restart of the resident HLE IOP's SIF services, and complete it on the EE's next `SMFLAG` observation:
  1. `process_sif_command`'s `SIF_CMD_RESET_CMD` case records the request (`arglen` at `+0x10`, `mode` at `+0x14`, both bounded), re-arms the RPCINIT handshake (`rpc_init_sent = false`, so the next `INIT_CMD` is answered again as after a real reboot) and marks a boot as pending.
  2. The first `sceSifGetReg(SMFLAG)` after that publishes `SIFINIT | CMDINIT | BOOTEND` (`0x70000`): the two modules the model actually stands in for have re-run their documented startup publication (`sifman` SIFINIT, `sifcmd` CMDINIT), and, because no IOP image is executed, the modelled boot has no further work and is complete. `SifIopSync` then observes `BOOTEND` and the guest resumes.
  3. `SIF_SYSREG_SUBADDR` stays zero: `sifcmd` re-publishes an IOP-RAM packet-buffer address there, which REPS2 does not model, so the EE takes its documented "CMDINIT handshake" branch and exchanges the command buffer through its own `INIT_CMD` payload rather than through an invented IOP address.
- **Scope and non-claims:** the requested IOP replacement image is **never executed**; no IOP RAM, R3000 code, module loading, IRX dependencies or IOP-side RPC server definitions are modelled. New services the rebooted IOP would provide (the CDVD/SIFRPC servers behind `IOPRP270.IMG`) remain absent, so a guest call to one still produces no reply and the caller stays blocked. The register file keeps its existing plain-store behaviour for guest writes; the hardware's write-one-to-clear on the IOP→EE flag register is not modelled, because REPS2 owns both sides of the register file and no observed guest path distinguishes the two — the completion publishes the IOP-set bits directly instead of relying on a clear-then-set exchange. `MSFLAG` is likewise unchanged.
- **Alternatives considered:**
  1. Leave the reset pending forever and stop at budget exhaustion — rejected: it is a dead end, and the observable requirement (the modelled resident IOP restarting its own services) is implementable without inventing device state.
  2. Report a fabricated `SifIopReset` success and skip the flag exchange — rejected: it would hide that the guest is waiting on a real, observable device transition.
  3. Execute the title's `IOPRP270.IMG` or the ROM `UDNL` loader — rejected: it is an R3000/IOP subsystem with its own boot chain, far outside the current vertical slice, and the image is copyrighted game/SDK data.
  4. Invent an IOP `SUBADDR` so the guest skips the CMDINIT branch — rejected: that address would be programmed into SIF DMA structures; ADR 0099 already refuses to fabricate it.
- **Consequences:** the retail post-reset path can leave `SifIopSync` and continue into the EE's re-initialisation (`sceSifInitRpc`, `sceSifInitCmd`, re-bind of the CDVD servers). Whatever the title does next is a new, unfaked observation: unimplemented services still stop the run as `unhandled_syscall`, and a server the rebooted IOP would have provided still answers nothing.
- **Observed (real-title probe, local evidence):** the regenerated probe on this revision reports `iop_resets=1 iop_resets_completed=1 last_reset_mode=0 last_reset_arg_len=32 sif_smflag=0x00070000`, re-runs the RPCINIT reply (`sif_rpcinit_sent=1 sif_ee_inbound=6 sif_ee_sreg0=1`) and completes a second CdInit bind and call (`sif_rpc_bind=2 sif_rpc_bind_sid=0x80000592 sif_rpc_call=2 sif_rpc_call_replies=2 sif_rpc_call_server=0x80000592`), stopping as `unhandled_syscall` `0x45` (`PollSema`) at `0x0025A734` after `3,172,908` instructions. The prior revision exhausted its 5,000,000-instruction budget in the `SifIopSync` poll at `0x0025ED10`. This is a post-reset runtime boundary, not a boot stage.
- **Validation:** `reps2_hle_syscall_codegen_smoke` adds two cases: a well-formed reset packet re-arms the handshake, records `arglen`/`mode` and becomes pending; the next `SMFLAG` read returns `0x70000` and completes the reset exactly once; the re-armed handshake then answers a following `INIT_CMD` with the documented `SIF_SREG_RPCINIT = 1` reply. A truncated reset packet (below `header + 8`) records nothing and leaves the handshake armed. The regenerated real-title probe is re-run on this revision and its post-reset trace recorded in `docs/RESEARCH.md` and `docs/PROJECT_STATE.md`.
