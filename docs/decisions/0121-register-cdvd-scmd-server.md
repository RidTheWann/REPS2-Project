# ADR 0121: Register the CDVDFSV S-command RPC server (`0x80000593`)

- **Status:** Accepted.
- **Date:** 2026-11-10.
- **Context:** The PostPR71 probe (after ADR 0120) exhausts its 5,000,000-instruction budget at `pc=0x002476B8` in the title's bind-retry loop: after the CdInit server and `ReferThreadStatus`, the title binds SIFRPC server `0x80000593` (`sif_rpc_bind_sid=0x80000593`, answered with the documented no-server reply, `sif_rpc_bind_had=0`), so the loop never sees a server and retries until the budget ends.
- **Evidence:**
  - **Observed (ps2tek, CDVDFSV RPC list):** `80000592h` CDVD Init, `80000593h` CDVD S commands, `80000595h` CDVD N commands, `80000597h` CDVD SearchFile, `8000059Ah` CDVD Disk Ready — all created by the IOP-side CDVDFSV module.
  - **Observed (PS2SDK `ee/rpc/cdvd/src/scmd.c`):** `#define CD_SERVER_SCMD 0x80000593`; `_CdCheckSCmd` binds that sid in a retry loop until `clientSCmd.server != 0`, and every S-command is issued as `sceSifCallRpc(&clientSCmd, <scmd code>, ...)` — the RPC function number IS the S-command number (`CD_SCMD_STATUS 0x0C`, `CD_SCMD_GETDISKTYPE 0x03`, `CD_SCMD_TRAYREQ 0x05`, ...). Replies start with the result word `m_retres`. The same file's `_CdCheckSCmd` does `PollSema(sCmdSemaId) != sCmdSemaId`, independently confirming the ADR 0119 success value (the semaphore id).
  - **Observed (PS2SDK `common/include/libcdvd-rpc.h`):** the `cdvdfsv_rpc3_*` in/out packet layouts for the S-command server (function `0x0B` is the generic apply-SCmd with a 20-byte `{cmdNum, inBuffSize, inBuff[16]}`).
  - **Observed (real-title probe, PostPR71 local evidence):** the bind for `0x80000593` is the frontier.
- **Decision:** Register sid `0x80000593` in the boot environment's SIFRPC server table with a handler that refuses every call. This makes the bind complete with the server's sid as the opaque token (the same reply shape CdInit gets), so the title's `_CdCheckSCmd` loop exits and the first S-command call reaches the dispatcher, where the generic fields record its function number (the S-command code) and first payload word. No reply is sent for any S-command yet: the handler returning false means no `SIF_CMD_RPC_END`, so the caller stays blocked — a truthful "not modelled" state, not a fabricated answer. The dispatch now also records the first payload word of every call (`last_rpc_call_request_word`) so the probe can name the request.
- **Alternatives considered:**
  1. Implement a guessed S-command (e.g. STATUS) without observing which one the title issues — rejected: the S-command code must come from the trace, not from a guess; a wrong reply would be a fabricated hardware answer.
  2. Keep the server unregistered and analyse the ELF statically — rejected: the probe names the exact S-command code and payload in one bounded run, which is cheaper and exact.
- **Consequences:** the bind loop completes and the next probe shows the first S-command number (`sif_rpc_call_number`) and request word, which names the next unit to model (an ISO-backed answer where the disc is involved). Until then the title blocks on the call's semaphore — the honest boundary.
- **Validation:** `reps2_hle_syscall_codegen_smoke` adds one case (122 total): the boot environment registers `0x80000593`, a bind returns its sid as the token, a call with function `0x0C` and no payload is recorded (`last_rpc_call_number == 0x0C`, matched server sid) but produces no reply and no semaphore signal, and a call with a payload records its first request word (`0xBEEF`) while still producing no reply. The regenerated PostPR72 probe then reports `sif_rpc_bind_had=1 sif_rpc_bind_server=0x80000593`, `sif_rpc_call_number=34` (0x22 `CD_SCMD_MMODE`), `rpc_call_req=0x00000002` (`SCECdMmodeDvd`), send/recv 4 bytes, and no reply: the title blocks on the call's semaphore (`stage=semaphore_wait_blocked`, `pc=0x0025A724`, 3,173,557 instructions). That names the next unit: implement the S-command the title issues first.
