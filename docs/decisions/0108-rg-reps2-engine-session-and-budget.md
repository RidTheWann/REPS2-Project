# ADR 0108: RG REPS2 ENGINE session and execution-budget contract

- **Status:** Accepted; lifetime contract extended for dynamic native modules.
- **Date:** 2026-11-09.
- **Context:** The first RG REPS2 ENGINE increment admitted a linked native function but did not yet own the EE state or memory needed to run a title module as an application session. The generated native build driver already exposes a guest-state initializer and a bounded CFG dispatcher, so the engine should consume those existing coarse-grained entry points rather than invent an interpreter or duplicate initialization.
- **Decision:** A prepared module must supply two functions: an initializer taking EeState plus an exact 32 MiB main-RAM image, and an execute function taking EeState plus an instruction budget. Engine admission validates both functions, the engine/runtime ABI versions, the name, and the host-native target.
- **Session ownership:** EngineSession owns one EeState and one 32 MiB main-RAM vector. It attaches EeState::memory.main_ram to that owned allocation before calling the generated initializer. An optional caller-supplied image must be exactly 32 MiB; an empty image means a zero-filled initial image. The initializer is invoked before the HLE and trace options are applied because the generated initializer resets HLE and host-observation state; the read-only media source is the exception and is attached first (see Session configuration).
- **Session configuration:** The session may enable the already-implemented EE syscall HLE boundary, enable the existing bounded instruction trace, and attach a host-owned read-only HostMediaSource. The source callback and context remain non-owning and must outlive the session. The media source is attached before the generated initializer runs, because the initializer resets only HLE and host-observation state and boot-time module code must be able to observe the host's source; otherwise every initialization-time disc read would fail closed against absent media.
- **Execution lifecycle:** A session transitions through empty, ready, running, paused, completed, and stopped. A bounded instruction-budget exhaustion is resumable: the next run call invokes the same generated CFG entry from the current guest PC. Status::ok marks completion. External control flow, guest exceptions, and unsupported runtime operations are reported as stops; they are not normalized into success. Per-run results retain the status, guest PC before/after, budget, and monotonic instruction-counter delta.
- **Performance boundary:** The engine calls the generated module once per run request. The generated CFG dispatcher continues to dispatch guest blocks and instructions inside native code. The engine adds no per-instruction callback, interpreter, worker thread, socket, or file I/O.
- **Lifetime and threading:** PreparedNativeModule owns a bounded copy of its module name and retains shared ownership of a dynamically loaded library. EngineSession copies that ownership, so the caller may release its own prepared handle after session start without invalidating callbacks. Static linked modules remain part of the process image. Dynamic libraries are pinned until process exit; hot-unload is unsupported. HostMediaSource callback/context remain non-owning and must outlive the session. EngineSession is one synchronous execution context and is not thread-safe; concurrent sessions require separate session objects and memory.
- **Alternatives considered:**
  1. Make the engine allocate/copy RAM inside a generated function or keep RAM on the stack — rejected because RAM ownership belongs to a host session and a 32 MiB automatic allocation is unsuitable.
  2. Add an instruction callback between Rust and C++ — rejected because it would add dispatch overhead to every guest instruction and split a verified native block's side effects.
  3. Return success after a budget limit or unsupported device access — rejected because it hides the exact guest execution boundary and breaks evidence-based compatibility reporting.
- **Consequences:** RG REPS2 ENGINE provides owned EE RAM, initializer handoff, resumable budget exhaustion, explicit stop states, structured execution counters, and a dynamic shared-module loader with an explicit ABI/lifetime contract. It is not a multi-threaded EE scheduler, complete PS2 runtime, cross-compiler, Android release backend, or real-title boot proof.
- **Validation:** The generated CFG CMake/CTest executable prepares the real synthetic initializer/dispatcher, verifies ABI rejection, validates RAM ownership and HLE configuration, forces a budget pause, resumes the same guest state, and asserts the real external-control-flow stop. A separate CTest loads an actual shared-library fixture, verifies descriptor and toolchain admission, missing-symbol/path rejection, transactional output preservation, and session retention after the caller drops its handle. CI must pass on Windows/MSVC and Linux/GCC.
