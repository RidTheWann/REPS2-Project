# ADR 0110: RG REPS2 ENGINE bounded host runner and JSON execution report

- **Status:** Accepted.
- **Date:** 2026-11-09.
- **Context:** The dynamic module loader and EngineSession can execute an AOT module, but only through C++ fixtures. Developers and IDE/AI agents need a real host executable that uses the same production loader/session APIs and reports guest stop conditions without equating a successful host invocation with a booted title.
- **Decision:** Build `rg-reps2-engine` as a standalone C++20 host executable linked to `RG::REPS2Engine`. It takes one explicit native-module path and supports an optional exact 32 MiB EE RAM image, an optional raw 2048-byte-sector ISO image, an instruction budget per run batch, a maximum number of resumable batches, optional EE syscall HLE and the bounded runtime instruction trace.
- **Execution semantics:** The runner loads the module through `NativeModuleLoader`, validates its ABI/target/toolchain fingerprint, constructs `SessionConfig`, starts one owned EngineSession, and loops only while the guest returns `instruction_budget_exhausted` and the configured batch cap remains. The same EE state/RAM is resumed; no session reset occurs between batches. Other guest statuses remain terminal and explicit.
- **Media semantics:** The runner owns the ISO file stream and installs a `HostMediaSource` callback that serves only in-range 2048-byte sectors. Reads are staged before copying to the runtime destination so a failed/short host read does not expose partial sector data. The runtime does not open files. Without `--media`, operations requiring media fail closed.
- **RAM semantics:** A supplied RAM image must be exactly 32 MiB. The runner's file buffer is copied into the EngineSession-owned RAM before the module initializer runs. Omitting `--ram` leaves the session's owned RAM zero-filled, which is useful for synthetic fixtures but is not a real-title boot configuration.
- **Reporting:** Successful bounded host execution emits exactly one JSON object with kind `rg.reps2.engine.run_report.v1`. It records engine/module identity, target, inputs, configuration, final session phase/PC, total guest instruction accounting, elapsed host microseconds, per-batch status/budget/PC/counter fields and optional trace PCs. Argument, image, loader and session errors emit `rg.reps2.engine.error.v1` with a stable error code. The process exit code indicates host/report success, not game boot/playability.
- **Safety and trust:** A native module is arbitrary in-process executable code. The runner is not a sandbox, and the optional ISO path is only a host media source; it does not confer trust on the module. Only trusted modules may be loaded. Module signatures and publisher policy remain separate work.
- **Validation:** CI runs the runner's help and version paths; a dedicated negative-path CTest invokes it without arguments, with a zero budget, and with a missing module path, asserting stable exit codes and parsing each error JSON envelope. As part of the native-build driver smoke, CI executes the exact generated synthetic DLL/SO through the standalone runner. CMake parses the success JSON and asserts the versioned kind, engine/module identity, final PC format and a positive guest instruction count on Windows/MSVC and Linux/GCC.
- **Consequences:** RG REPS2 ENGINE can now be exercised as a standalone host application and its run result can be consumed by automation without parsing terminal prose. This does not claim a real PS2 title boot, full system services, Android release support or a performance improvement.
