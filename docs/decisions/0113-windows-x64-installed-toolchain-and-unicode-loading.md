# ADR 0113: Windows x64 installed toolchain and Unicode native-module loading

- **Status:** Accepted.
- **Date:** 2026-11-09.
- **Context:** Windows x64 is the first-class desktop delivery target. Passing an in-tree MSVC build does not prove the installed executable, static library, headers, runtime dependencies, or paths with spaces/non-ASCII characters work after deployment. The engine must be consumable by an independent C++ application as well as by its own runner.
- **Decision:** Treat the Windows CMake install tree as a release-validation boundary. Install the Rust frontend and RG REPS2 ENGINE runner into `bin/`, the engine static library into `lib/`, and the runtime/engine public headers under `include/`. On MSVC, include `InstallRequiredSystemLibraries` so the C/C++ runtime DLLs required by the installed host are staged beside the executables. This is a developer SDK/toolchain install tree, not a polished installer or consumer game launcher.
- **Unicode process contract:** Use `wmain` for the Windows runner. Convert each UTF-16 process argument strictly to UTF-8, construct filesystem paths from `std::u8string`, and serialize module/RAM/media paths with `generic_u8string`. Keep the Windows dynamic loader on `LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`. Do not route paths through the active ANSI code page or fall back to unrestricted DLL search.
- **Install-tree validation:** A Windows x64 PowerShell smoke test runs after CTest. It installs into a fresh path containing spaces and non-ASCII characters, checks the frontend/runner/static library/public headers/staged MSVC runtime/`LICENSE`, then changes the working directory outside the build tree. It copies the generated synthetic native DLL to a Unicode plugin path, loads/runs it through the installed runner, parses the JSON report, verifies the path round-trip and positive guest instruction accounting, and builds/runs an independent C++ consumer that uses only the installed public headers and static library.
- **Bundle self-containment:** The portable ZIP must run with the install tree removed from `PATH`. The relocated runner and the extracted-SDK consumer execute with a `PATH` containing only the bundle's `bin` and system directories, so a DLL missing from the ZIP cannot be satisfied from the original install. `bundle.json` records the reviewed source commit (the PR head on `pull_request` events, not the ephemeral merge commit) and both the engine and runtime ABI versions; the extracting script asserts those values. The manifest and checksum list are UTF-8 without a BOM and use LF endings so strict JSON readers and `sha256sum -c` accept them. Every extracted file must appear in the checksum manifest, and entries that are absolute or escape the extraction root are refused; only `checksums.sha256` itself is exempt. The same test creates a relocatable ZIP with a versioned bundle manifest and UTF-8 SHA-256 payload list, extracts it to a second Unicode path, verifies every payload digest, reruns the native DLL through the relocated runner, and builds/runs another C++ consumer against the extracted SDK. CI uploads the ZIP plus an outer SHA-256 sidecar.
- **Platform scope:** Windows/MSVC is the active delivery gate. Linux/GCC remains a portability regression target. Android and macOS are deferred and must not hold up the Windows desktop path.
- **Validation:** Passed on 2026-11-09 in workflow run [42621639813](https://github.com/RidTheWann/REPS2-Project/actions/runs/42621639813), commit `27c3996`: Windows/MSVC Rust gates, CMake Release build, all 40 CTests, staged install, Unicode DLL load/path round-trip, independent installed C++ consumer, portable ZIP creation, UTF-8 per-file SHA-256 verification, Unicode extraction/relocation, relocated DLL execution and a second C++ consumer against the extracted SDK. The ZIP and outer SHA-256 sidecar were uploaded as artifact `rg-reps2-engine-windows-x64-msvc` (artifact ID `13676302668`, about 1.34 MB). Linux/GCC, Rust MSRV 1.88 and dashboard jobs also passed.
- **Consequences:** A green in-tree build is no longer the only evidence: CI will verify a staged Windows toolchain can execute a generated DLL and support an external C++ consumer from an unrelated working directory. This does not establish a signed installer, trusted third-party module distribution, retail-title boot, game playability, or performance improvement.
