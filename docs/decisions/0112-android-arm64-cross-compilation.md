# ADR 0112: Android arm64-v8a NDK cross-compilation boundary

- **Status:** Deferred.
- **Date:** 2026-11-09.
- **Context:** RG REPS2 ENGINE already identifies Android/AArch64 as target properties and its POSIX dynamic-loader branch uses `dlopen`/`dlsym`, but Windows/Linux CI did not prove that the engine runner or frontend-generated native modules compile for an Android ABI. The generated AOT artifact is C++20, so the appropriate first Android gate is an official NDK cross-build, not an unverified custom AArch64 machine-code backend.
- **Decision:** Add a dedicated Ubuntu CI job using the Android NDK CMake toolchain file. Pin NDK r30 package `30.0.16248370`, `ANDROID_ABI=arm64-v8a`, `ANDROID_PLATFORM=android-24`, and `ANDROID_STL=c++_shared` for reproducibility. Build the standalone engine runner and a synthetic frontend-generated native shared module. The Rust frontend remains a host executable; only the C++ engine and generated module are cross-compiled.
- **Target identity:** Compile a probe with the NDK's `aarch64-linux-android24-clang++` and use `static_assert` to require `current_native_target().architecture == arm64` and `operating_system == android`. This ensures the descriptor's compile-time target detection is exercised under the Android compiler macros.
- **Artifact validation:** Use NDK LLVM `readelf` to assert that both the runner and generated module are AArch64 ELF, that the module exports `rg_reps2_get_native_module_descriptor_v1`, and that the runner/module depend on `libc++_shared.so`. Upload the binaries and inspection reports as a CI artifact for 14 days.
- **Explicit non-goals:** Do not execute the ARM64 Android binaries on x86-64 CI. This job does not prove `dlopen` works on a real Android device, does not validate C++ shared-STL packaging in an APK, and does not implement Gradle, JNI, Android app lifecycle, storage integration, Vulkan/GPU, audio or input backends. API 24 is only this CI compilation target; it is not a product `minSdkVersion` choice.
- **Validation:** The `android-arm64-cross-compile` workflow job must build both targets, pass target static assertions, pass ELF machine/symbol/STL checks, and upload the resulting artifact. Windows/Linux runtime-loading CI remains independently required.
- **Consequences:** The project obtains repeatable evidence that its engine/session C++ and generated module wrapper compile for Android arm64-v8a. This narrows the portability gap but leaves Android loader runtime tests and mobile product integration as separate future gates. It does not establish playable PS2 titles or performance.
